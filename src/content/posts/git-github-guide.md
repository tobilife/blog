# Git/GitHub 명령어 완벽 가이드 (초보자를 위한 상세 설명)

이 문서는 Git과 GitHub를 사용하여 프로젝트를 효율적으로 관리하고 협업하는 데 필요한 핵심 명령어들을 초보자의 눈높이에 맞춰 설명합니다. 각 명령어의 개념과 사용법, 그리고 실제 시나리오에서의 활용법을 예시와 함께 제공합니다.

---

## 1. 시작하기: Git 및 환경 설정 (시스템적인 요소 포함)

### 1.1. Git 설치 확인
Git이 컴퓨터에 제대로 설치되었는지 확인하는 명령어입니다.

```bash
$ git --version
```

**설명:** 이 명령어를 실행했을 때 Git 버전 정보(예: `git version 2.xx.x`)가 표시된다면<br>Git이 정상적으로 설치된 것입니다. 만약 오류가 발생한다면 Git을 설치해야 합니다.

### 1.2. 사용자 정보 설정
Git 커밋에 사용자 이름과 이메일 주소를 기록하도록 설정합니다.<br>이 정보는 사용자이 만든 커밋을 식별하는 데 사용됩니다.

#### 사용자 이름 설정

```bash
$ git config --global user.name "사용자의 이름"
```

#### 사용자 이메일 설정

```bash
$ git config --global user.email "사용자의 이메일@example.com"
```

**설명:** `--global` 옵션은 이 설정을 사용자의 컴퓨터에 있는 모든 Git 저장소에 적용합니다.<br>특정 저장소에만 다른 설정을 하고 싶다면 해당 저장소에서 `--global` 없이 명령어를 실행하면 됩니다.

### 1.3. 기본 브랜치 이름 설정
새로운 Git 저장소를 초기화할 때 기본 브랜치 이름을 `master` 대신 `main`으로 설정하도록 합니다.<br>최근에는 `main`을 기본 브랜치 이름으로 사용하는 추세입니다.

```bash
$ git config --global init.defaultBranch main
```

**설명:** 이 설정을 해두면 앞으로 `git init`으로 새로운 저장소를 만들 때 자동으로 `main` 브랜치가 생성됩니다.

### 1.4. 기본 텍스트 에디터 설정 (선택 사항)
Git은 커밋 메시지를 작성하거나 병합 충돌을 해결할 때 텍스트 에디터를 엽니다.<br>기본으로 열릴 에디터를 지정할 수 있습니다.

#### VS Code를 기본 에디터로 설정하는 예시

```bash
$ git config --global core.editor "code --wait"
```

**설명:** `code --wait`는 VS Code가 닫힐 때까지 Git이 기다리도록 하는 옵션입니다.<br>다른 에디터를 사용한다면 해당 에디터의 실행 명령어를 사용하세요 (예: `nano`, `vim`, `subl -w` 등).

## 2. 로컬 저장소 생성 및 관리의 기본

### 2.1. 새로운 로컬 저장소 초기화
아직 Git으로 관리되지 않는 폴더를 Git 저장소로 만들 때 사용합니다.

```bash
$ git init
```

**설명:** 이 명령어를 실행하면 현재 디렉토리 안에 `.git`이라는 숨김 폴더가 생성됩니다.<br>이 폴더가 Git 저장소의 모든 정보를 담고 있습니다.

### 2.2. 원격 저장소 복제 (Clone)
GitHub(또는 다른 원격 Git 저장소)에 있는 기존 프로젝트를<br>내 컴퓨터로 통째로 복사해 올 때 사용합니다.

```bash
$ git clone [GitHub 저장소 URL]
```

**예시:**

```bash
$ git clone https://github.com/your-username/your-repository.git
```

**설명:** 이 명령어를 실행하면 해당 GitHub 저장소의<br>모든 파일과 Git 이력이 현재 디렉토리 아래의 새로운 폴더로 복사됩니다.<br>복사된 폴더는 자동으로 원격 저장소(`origin`이라는 이름으로)와 연결됩니다.

### 2.3. 파일 상태 확인
현재 작업 디렉토리에 있는 파일들의 Git 관리 상태를 보여줍니다.<br>어떤 파일이 변경되었고, 스테이징되었는지 등을 알 수 있습니다.

```bash
$ git status
```

**설명:** Git 작업을 할 때 가장 자주 사용하는 명령어 중 하나입니다.<br>커밋하기 전에 항상 이 명령어로 변경사항을 확인하는 습관을 들이세요.

### 2.4. 변경사항 스테이징 (Staging)
수정하거나 새로 생성한 파일들을 Git이 다음 커밋에 포함할 수 있도록<br>'준비 영역(Staging Area)'에 올립니다.<br>스테이징되지 않은 파일은 커밋되지 않습니다.

#### 변경될 파일 하나만 스테이징

```bash
$ git add [파일명]
```

**예시:**

```bash
$ git add index.html
```

#### 모든 변경된 파일 스테이징

```bash
$ git add .
```

**설명:** `git add .`은 현재 디렉토리 및 하위 디렉토리의<br>모든 변경사항(새 파일, 수정된 파일)을 스테이징합니다.<br>삭제된 파일까지 포함하려면 `git add -A`를 사용합니다.

### 2.5. 변경사항 커밋 (Commit)
스테이징된 변경사항들을 확정하고, 변경 내용에 대한 의미 있는 설명을 기록합니다.<br>커밋은 프로젝트 이력의 한 '스냅샷'입니다.

```bash
$ git commit -m "커밋 메시지"
```

**예시:**

```bash
$ git commit -m "feat: 로그인 기능 추가 및 UI 개선"
```

**설명:** `-m` 옵션 뒤에 커밋 메시지를 직접 입력합니다.<br>메시지는 간결하고 명확하게 작성하는 것이 좋습니다. `-m` 옵션 없이 `git commit`만 실행하면<br>설정된 기본 에디터가 열리고 메시지를 작성할 수 있습니다.

## 3. 원격 저장소 (GitHub)와의 연동

### 3.1. 원격 저장소 연결
`git init`으로 생성한 로컬 저장소를 GitHub에 있는 특정 저장소와 연결합니다.<br>`origin`은 관례적으로 사용되는 원격 저장소의 별칭입니다.

```bash
$ git remote add origin [GitHub 저장소 URL]
```

**예시:**

```bash
$ git remote add origin https://github.com/your-username/new-project.git
```

**설명:** 이 명령어는 로컬 저장소와 원격 저장소 사이에 '링크'를 만듭니다.<br>이렇게 연결되어야 `git push`나 `git pull` 같은 명령어를 사용할 수 있습니다.

### 3.2. 원격 저장소 목록 확인
현재 로컬 저장소에 어떤 원격 저장소들이 연결되어 있는지,<br>그리고 각각의 URL은 무엇인지 확인합니다.

```bash
$ git remote -v
```

**설명:** `-v` (verbose) 옵션은 원격 저장소의 이름과 함께 그 URL을 표시해줍니다.

### 3.3. 로컬 변경사항 푸시 (Push)
로컬에서 커밋한 내용을 GitHub 저장소로 업로드하여 다른 사람들과 공유하고 원격 저장소의 이력을 업데이트합니다.

```bash
$ git push origin [브랜치 이름]
```

**예시 (첫 푸시 시, `-u` 옵션으로 추적 설정):**

```bash
$ git push -u origin main
```

**설명:** `origin`은 연결된 원격 저장소의 이름이고,<br>`main`은 푸시할 로컬 브랜치 이름입니다.`-u` 또는 `--set-upstream` 옵션은<br>해당 로컬 브랜치가 `origin/main`을 추적하도록 설정하여,<br>다음부터는 단순히 `git push`만으로도<br>해당 브랜치로 푸시할 수 있게 합니다.

### 3.4. 원격 변경사항 가져오기 (Fetch)
GitHub의 최신 변경사항을 로컬로 가져오지만,<br>아직 사용자의 작업 브랜치에 병합하지는 않습니다.<br>어떤 변경사항이 있는지 먼저 보고 싶을 때 유용합니다.

```bash
$ git fetch origin
```

**설명:** 이 명령어는 원격 저장소의 최신 이력(커밋, 브랜치 정보 등)을 로컬에 업데이트합니다.<br>하지만 현재 작업 중인 브랜치의 파일 내용은 변경되지 않습니다.<br>`git status`를 다시 실행하면 원격 저장소와의 동기화 상태를 볼 수 있습니다<br>(예: `Your branch is behind 'origin/main' by 2 commits, and can be fast-forwarded.`).

### 3.5. 원격 변경사항 병합 (Pull)
`git fetch`와 `git merge`를 동시에 수행하는 명령어입니다.<br>GitHub의 최신 코드를 내 로컬 브랜치에 반영합니다.

```bash
$ git pull origin [브랜치 이름]
```

**예시 (추적 브랜치가 설정된 경우):**

```bash
$ git pull
```

**설명:** 다른 사람이 GitHub에 푸시한 변경사항을<br>내 컴퓨터로 가져와서 내 작업과 합칠 때 사용합니다.<br>협업 시에는 `git pull`을 자주 사용하여<br>최신 상태를 유지하는 것이 중요합니다.

## 4. 브랜치 (Branch) 관리

### 4.1. 브랜치 생성
기존 코드 베이스를 바탕으로 독립적인 작업 공간을 만듭니다.<br>새로운 기능 개발이나 버그 수정 시 메인 코드에 영향을 주지 않고 작업할 수 있습니다.

```bash
$ git branch [새로운 브랜치 이름]
```

**예시:**

```bash
$ git branch feature/login
```

**설명:** 이 명령어는 새 브랜치를 만들지만, 현재 작업 중인 브랜치는 변경되지 않습니다.

### 4.2. 브랜치 전환
여러 브랜치 사이를 오가며 다른 작업을 할 수 있게 해줍니다.

#### 기존 브랜치로 이동

```bash
$ git checkout [이동할 브랜치 이름]
```

**예시:**

```bash
$ git checkout main
```

#### 새 브랜치 생성과 동시에 전환

```bash
$ git checkout -b [새로운 브랜치 이름]
```

**예시:**

```bash
$ git checkout -b hotfix/bug-fix-123
```

**설명:** `checkout` 명령은 해당 브랜치의 최신 커밋 상태로 작업 디렉토리의 파일들을 변경합니다.<br>`-b` 옵션은 브랜치 생성과 동시에 그 브랜치로 이동하는 편리한 단축 명령입니다.

### 4.3. 브랜치 목록 확인
현재 로컬 저장소에 존재하는 브랜치들을 확인합니다.<br>어떤 브랜치에서 작업 중인지도 알 수 있습니다.

#### 로컬 브랜치 목록 확인

```bash
$ git branch
```

#### 모든 브랜치 (로컬 + 원격) 확인

```bash
$ git branch -a
```

**설명:** 현재 활성화된 브랜치 앞에는 `*` 표시가 붙습니다.

### 4.4. 브랜치 병합 (Merge)
다른 브랜치에서 작업한 내용을 현재 브랜치로 통합합니다.<br>예를 들어, `feature/login` 브랜치에서 만든 로그인 기능을 `main` 브랜치에 합칠 때 사용합니다.

```bash
$ git merge [병합할 브랜치 이름]
```

**예시 (main 브랜치에서 feature/login 브랜치 병합):**

1.  먼저 `main` 브랜치로 이동합니다:
    ```bash
    $ git checkout main
    ```
2.  `feature/login` 브랜치를 `main`에 병합합니다:
    ```bash
    $ git merge feature/login
    ```

**설명:** 병합 과정에서 두 브랜치에서 같은 파일을 다르게 수정했다면<br>**병합 충돌(Merge Conflict)**이 발생할 수 있습니다.<br>이 경우, 충돌을 수동으로 해결해야 합니다 (아래 '고급 사용 및 문제 해결' 섹션 참조).

### 4.5. 브랜치 삭제
더 이상 필요 없는 브랜치를 로컬 및 원격 저장소에서 제거합니다.

#### 로컬 브랜치 삭제 (병합된 경우)

```bash
$ git branch -d [삭제할 브랜치 이름]
```

**예시:**

```bash
$ git branch -d feature/login
```

**설명:** `-d` 옵션은 해당 브랜치가 현재 브랜치에 완전히 병합된 경우에만 삭제를 허용합니다.<br>안전하게 브랜치를 삭제할 때 사용합니다.

#### 로컬 브랜치 강제 삭제 (병합되지 않은 변경사항이 있어도 삭제)

```bash
$ git branch -D [삭제할 브랜치 이름]
```

**주의:** `-D` 옵션은 병합되지 않은 변경사항이 있어도 강제로 브랜치를 삭제하므로,<br>**데이터 손실의 위험**이 있습니다. 신중하게 사용해야 합니다.

#### 원격 브랜치 삭제

```bash
$ git push origin --delete [원격 브랜치 이름]
```

**예시:**

```bash
$ git push origin --delete feature/login
```

**설명:** 이 명령어는 GitHub와 같은 원격 저장소에서 해당 브랜치를 삭제합니다.

## 5. 커밋 히스토리 확인 및 조작

### 5.1. 커밋 로그 확인
지금까지 커밋된 모든 변경 이력을 시간 순서대로 보여줍니다.<br>누가 언제 어떤 내용을 커밋했는지 확인할 수 있습니다.

#### 기본 커밋 목록 확인

```bash
$ git log
```

#### 간결하고 그래프 형태로 보기 (강력 추천!)

```bash
$ git log --oneline --graph --all
```

**설명:**
*   `--oneline`: 각 커밋을 한 줄로 간결하게 표시합니다.
*   `--graph`: 브랜치 및 병합 이력을 아스키 그래프로 보여줍니다.
*   `--all`: 현재 브랜치뿐만 아니라 모든 로컬 및 원격 브랜치의 이력을 보여줍니다.
이 외에도 `git log --pretty=format:"..."`과 같은 다양한 옵션으로 원하는 형식으로 로그를 출력할 수 있습니다.

### 5.2. 커밋 되돌리기 (Revert)
특정 커밋에서 발생한 변경사항을 취소하는 새로운 커밋을 생성합니다.<br>기존 커밋을 삭제하지 않고 변경 이력을 남기므로,<br>**이미 공유된 커밋을 되돌릴 때 안전하게 사용할 수 있습니다.**

```bash
$ git revert <커밋 해시>
```

**예시:**

1.  `git log`로 되돌리고 싶은 커밋의 해시(commit ID)를 확인합니다.
2.  예시: `ab12cd34` 커밋을 되돌립니다:
    ```bash
    $ git revert ab12cd34
    ```

**설명:** 이 명령어를 실행하면 해당 커밋에서<br>변경된 내용을 반대로 적용하는 새로운 커밋이 자동으로 생성됩니다.<br>이 커밋을 푸시하면 다른 사람들도 어떤 변경이 되돌려졌는지 알 수 있습니다.

### 5.3. 커밋 수정 (Amend)
가장 최근의 커밋 메시지를 수정하거나,<br>스테이징 영역에 추가 변경사항을 포함하여 하나의 새로운 커밋으로 만듭니다.<br>**이미 푸시한 커밋에는 사용하지 않는 것이 좋습니다.** (히스토리가 변경되기 때문)

```bash
$ git commit --amend
```

**설명:**
*   커밋 메시지만 수정하고 싶다면, 변경사항 없이 `git commit --amend`를 실행하면 에디터가 열립니다.
*   최근 커밋에 빠뜨린 파일이나 수정을 추가하고 싶다면,<br>파일을 수정하고 `git add [파일명]` 후 `git commit --amend`를 실행합니다.<br>
이는 이전 커밋을 '덮어쓰는' 방식으로 동작하므로,<br>아직 GitHub에 푸시하지 않은 로컬 커밋에만 사용하는 것이 안전합니다.

## 6. 고급 사용 및 문제 해결

### 6.1. 병합 충돌 해결
두 브랜치의 같은 파일을 동시에 수정하여<br>Git이 자동으로 병합할 수 없을 때 '충돌'이 발생합니다.<br>Git은 충돌이 난 부분을 표시해주고,<br>개발자가 수동으로 해결하도록 합니다.

1.  **충돌 발생 확인:** `git merge` 또는 `git pull` 시 충돌 메시지가 뜨거나<br>`git status`에서 'unmerged paths'가 보입니다.<br>
    ```bash
    $ git status
    ```
2.  **충돌 파일 수정:** 충돌이 난 파일을 텍스트 에디터로 엽니다.<br>Git은 충돌 부분을 다음과 같이 표시합니다:
    ```
    <<<<<<< HEAD
    // 현재 브랜치의 내용
    =======
    // 병합하려는 브랜치의 내용
    >>>>>>> [브랜치 이름]
    ```
    두 내용 중 유지하고 싶은 부분을 선택하거나,<br>새로운 코드를 작성하여 충돌 마커를 모두 제거합니다.
3.  **해결된 파일 스테이징:** 충돌을 해결한 후 파일을 스테이징합니다.
    ```bash
    $ git add [충돌 해결된 파일명]
    ```
4.  **병합 커밋 완료:** 모든 충돌 파일이 스테이징되었다면, 병합 커밋을 완료합니다.
    ```bash
    $ git commit
    ```
    (별도의 메시지를 입력하지 않으면 Git이 기본 병합 메시지를 제공합니다.)

**설명:** 충돌 해결은 Git 협업에서 매우 중요한 부분입니다.<br>차분히 내용을 확인하고 올바르게 합치는 연습이 필요합니다.

### 6.2. 작업 임시 저장 (Stash)
아직 커밋할 준비가 되지 않은 변경사항들을 임시로 저장하여,<br>현재 작업 디렉토리를 깨끗하게 만든 후<br>다른 브랜치로 전환하거나 긴급한 작업을 처리할 때 사용합니다.

#### 현재 작업 내용을 임시로 저장

```bash
$ git stash
```

**또는 메시지와 함께 저장:**

```bash
$ git stash save "로그인 기능 작업 중"
```

#### 저장된 스태시 목록 확인

```bash
$ git stash list
```

#### 가장 최근 저장 내용 적용 및 삭제

```bash
$ git stash pop
```

#### 특정 저장 내용 적용 (삭제 안 함)

```bash
$ git stash apply stash@{1}
```

**설명:** `stash`는 현재 작업 중인 내용을 잠시 보류해두고 싶을 때 유용합니다.<br>`pop`은 적용 후 스태시 목록에서 해당 항목을 삭제하고,<br>`apply`는 적용만 하고 삭제하지 않습니다.

### 6.3. .gitignore 파일 사용
Git이 버전 관리에 포함하지 않을 파일이나 디렉토리를 지정합니다.<br>빌드 결과물, 로그 파일, 개인 설정 파일 등 <br>저장소에 불필요한 파일들이 커밋되는 것을 방지합니다.

**사용법:**

1.  프로젝트의 루트 디렉토리에 `.gitignore` 파일을 생성합니다.
2.  파일 내부에 Git이 무시할 파일이나 디렉토리 패턴을 한 줄에 하나씩 작성합니다.

**`.gitignore` 파일 내용 예시:**

```gitignore
# 빌드 아티팩트
/build
/dist
*.o
*.a

# 의존성 디렉토리
node_modules/

# 로그 파일
*.log
npm-debug.log*

# 운영체제 관련 파일
.DS_Store
Thumbs.db

# 개인 설정 파일 (예: API 키)
config.local.js
.env
```

**설명:**
*   `#`으로 시작하는 줄은 주석입니다.
*   디렉토리 이름 뒤에 `/`를 붙이면 해당 디렉토리 전체를 무시합니다 (예: `node_modules/`).
*   `*`는 와일드카드 문자로 어떤 문자열이든 일치합니다 (예: `*.log`는 모든 .log 파일).
*   `!`는 특정 파일이나 디렉토리를 무시하지 않도록 예외 처리할 때 사용합니다 (예: `!important.log`).
`.gitignore`에 추가된 파일들은 `git add`나 `git commit` 시 무시되므로, 깔끔한 저장소 관리에 필수적입니다.
